## Findings

1. **P1: Rejected or edited supporting evidence never invalidates an approved design.** Locations: `apps/api/galvanise/services/design.py:84-95,169-174`; `apps/api/galvanise/services/knowledge.py:15-19`. `input_versions` contains only prior design artifact kinds, while evidence validation checks project membership without status/version. Reproduction against the real API: link an approved `evidence` record in a validation's `payload.evidence_ids`, save pending and approve the validation, then PATCH the evidence to `rejected`. All three operations return 200; GET design still returns validation `status=approved`, `payload.stale=false`, `readiness.validation=true`, and no findings. Editing the evidence likewise escapes the snapshot. Track referenced evidence versions/status and invalidate dependent reasoning when its supporting evidence is rejected or changes; apply the same checks to generated evidence links.

2. **P2: An approved component can carry an unreviewed dependency into apparently ready validation.** Locations: `apps/api/galvanise/services/design.py:105-107,136-139,240-244`. Dependencies intentionally accept pending same-batch components, but neither freshness nor usability subsequently checks their review state. Reproduction: generate Workflow A depending on Supplier access B, approve only A, generate a validation referencing A, then approve that validation. The API permits every step; B remains pending, all five readiness flags are true, and findings are empty. The real frontend displays “Input versions match” and “Reviewed validation inputs are available.” Keep pending dependencies valid during proposal creation, but check dependency approval/currentness before treating their consuming component as usable; handle cycles with a visited set rather than unguarded recursion.

3. **P2: Source evidence is silently omitted/truncated before design context accounting.** Locations: `apps/api/galvanise/services/design.py:320-321,353-365`; inherited helper `apps/api/galvanise/services/knowledge.py:71-88`. Reproduction in the isolated persisted project: insert 13 source documents, each 5,001 characters followed by an important exception, then call `context_for(..., 'validation')`. Only 12 documents reach the provider, each exactly 5,000 characters; every reported `context_limits` value is zero, including `documents_omitted_for_budget`. Message count/text limits and knowledge description excerpts have the same accounting gap. Count initial omissions and per-source text truncation, not just later budget removals, and persist those limits so findings warn about evidence the model never saw.
