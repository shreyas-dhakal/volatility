# Guided volatility-based system design

Approved direction: the user confirmed the method described in conversation and explicitly authorized full implementation and Orca Codex worktrees. This document records implementation decisions within that authorization.

## Intent
Help software teams turn gathered use cases into a defensible system design using volatility-based decomposition inspired by Righting Software. Preserve business essence and detailed variations, identify independent reasons for change, propose responsibilities that hide them, and validate behavior coverage and change containment. Source code is optional.

## Approach
Considered prompt-only architecture generation (existing behavior), an explicit reviewed design model integrated with current persistence (chosen), and a separate autonomous design service (unnecessary infrastructure). Extend the existing FastAPI/PostgreSQL knowledge model and Next workspace. Do not replace working chat, sources, graph, or review features.

## Workflow and artifacts
1. Gather structured use cases with actors, trigger, preconditions, steps, outcomes, and variations. Retain original cases and document evidence.
2. Propose core use cases expressing business essence, with explicit mappings to original use cases, rationale, and unresolved cases. Similar wording is not enough.
3. Propose volatility records: what changes, why plausible, over-time/across-customer axis, examples, stable aspects, supporting case/evidence IDs, uncertainty and questions. Do not equate variability, churn, or every variation with architectural volatility.
4. Propose components encapsulating identified volatilities. Classify client, manager, engine, resource_access, resource, utility. Explain responsibility, hidden change, stable contract, exclusions, and dependencies. Separate workflow sequence from business activity implementation. Do not turn each use case/entity into a service. Deployment is a separate decision.
5. Propose use-case collaborations and change-containment scenarios. Independently check actual references, missing coverage, missing contracts, unmapped volatility, unknown dependencies, and dependency cycles. AI findings are qualitative proposals, never verified execution or a numeric architecture score.
6. Review all artifacts through existing human review with optimistic versions/history. Show a traceable reasoning chain and invalid/stale assumptions. Re-running generation preserves approved records; historical validation must not masquerade as validation of an updated design.

## Shared API contract (backend and frontend workers)
KnowledgeRecord serialized shape remains existing {id,project_id,kind,title,description,status,evidence_status,payload,version,history,...}. Add polymorphic kinds use_case, core_use_case, design_validation; existing volatility and boundary kinds are used for design artifacts. Tag generated design records payload.design_engine=true; use-case records are native to this workflow. No schema migration needed for string discriminator additions.

GET /api/projects/{project_id}/design returns {use_cases: KnowledgeRecord[], core_use_cases: KnowledgeRecord[], volatilities: KnowledgeRecord[], components: KnowledgeRecord[], validations: KnowledgeRecord[], findings: [{code:string,severity:string,message:string,record_ids:string[]}], readiness: {use_cases:boolean,core_use_cases:boolean,volatility:boolean,decomposition:boolean,validation:boolean}}. Findings are deterministic checks, readiness indicates reviewed usable stage inputs (not design correctness). Include metadata needed to detect stale validations in payloads. Bound context and lists; expose truncation when inputs exceed supported bounds.

POST /api/projects/{project_id}/design/use-cases accepts {title:string,description:string,actor:string,trigger:string,preconditions:string[],steps:string[],outcome:string,variations:string[],evidence_ids:string[]} and returns KnowledgeRecord. Human-authored remains pending, human_confirmed evidence, review separately. Validate project-owned evidence; reject empty title/steps/outcome and bounded fields. UI may use sensible defaults for optional fields.

POST /api/projects/{project_id}/design/generate accepts {stage:'core'|'volatility'|'decomposition'|'validation'} and returns {records:KnowledgeRecord[]}. Use real configured structured OpenAI calls; missing config 503; no fake data. Require use cases for core, reviewed core cases for volatility, reviewed volatilities/core cases for decomposition, reviewed components for validation; actionable 422 when missing inputs. Allow original approved inputs from previous stages and preserve review boundaries. Stage generation is explicit; no auto approval.

Payload conventions: core.use_case_ids:string[]; volatility.core_use_case_ids:string[],axis:string,what_changes:string,why_plausible:string,stable_aspects:string[],examples:string[]; boundary.component_role:string,volatility_ids:string[],responsibility:string,hidden_change:string,stable_contract:string,excluded_responsibilities:string[],dependencies:string[] (component IDs or same-batch component titles resolved by backend); validation payload includes collaborations:[{core_use_case_id:string,component_ids:string[],steps:string[]}], scenarios:[{title:string,volatility_id:string,changed_component_ids:string[],unchanged_component_ids:string[],rationale:string}], assumptions:string[], input_versions:object. Backend may add fields; frontend renders additional readable fields. All references must belong to project and correct artifact kind. Generated nonempty required links and contracts enforced. Validation scenarios must refer to current components and known volatilities.

## Constraints and acceptance
Single-owner MVP remains explicit; team collaboration means a team can use the design process, not new membership/SSO infrastructure. Preserve original use cases, factual uncertainty, historical proposals and human approvals. No invented code, confidence, cost or execution claims. Protect against untrusted source instructions and cross-project references. Stale edits return 409. No API key in browser. Follow Astryx guidance, existing page frame, component docs, and built doctor. Tests must cover owner isolation, missing prerequisites/config, invalid AI references, approval preservation, core-to-detail mapping, independent volatility reasoning, component contracts, deterministic findings, and stale validation. Verify backend suite, frontend tests/build, browser workflow and doctor. Credentials-free checks must not claim live AI verification.
