# Build Galvanise — AI-Powered System Architecture Workspace

You are a senior full-stack engineer and AI systems architect. Build a complete, working MVP of **Galvanise**, a chat-first AI platform for volatility-based software architecture discovery, system design, and legacy modernisation planning.

Do not build a landing page, static prototype, or mock-only application. Build the actual functional product with a working backend, database, AI conversations, account connections, project workspaces, and architecture analysis.

Make reasonable engineering decisions independently. Prioritise a polished, working end-to-end application over unnecessary complexity.

## 1. Product vision

Galvanise helps companies understand their existing software, identify which business decisions and requirements are likely to change, and design better software architectures using **volatility-based decomposition**.

The central experience is an AI-powered chat workspace.

Users should be able to:

1. Sign in and connect their GitHub account.
2. Create a project and connect an existing repository.
3. Upload business requirements, architecture documents, meeting transcripts, and technical specifications.
4. Explain their business and its future plans through natural-language chat.
5. Have an AI architect analyse the business and codebase.
6. Discover independent sources of business and technical volatility.
7. Answer targeted questions generated by the AI.
8. View a continuously updated knowledge graph and volatility model.
9. Generate and compare alternative software architectures.
10. View recommended architectural boundaries, supporting evidence, tradeoffs, and possible migration approaches.

The system must distinguish between verified facts, AI inferences, and unconfirmed hypotheses.

The AI should never assume that every application requires microservices or that every volatile business rule requires a separate service.

## 8. Persistent business knowledge

A central feature is extracting structured business knowledge from conversations and uploaded documents.

Create database models for:

- Project
- Conversation
- Message
- ConnectedSource
- SourceDocument
- BusinessRequirement
- BusinessDecision
- ChangeDriver
- VolatilityHypothesis
- StakeholderQuestion
- StakeholderAnswer
- ArchitectureCandidate
- ArchitectureBoundary
- EvidenceReference
- TechnicalGraph
- TraceabilityLink

For example, a user says:

"We plan to add several suppliers next year. Every supplier has a different API, but our purchasing process should remain the same."

The system should identify:

Business decision:
Support multiple suppliers.

Change driver:
Supplier expansion.

Volatile concern:
Supplier-specific API protocols and mappings.

Potential invariant:
Internal purchasing workflow should remain stable.

Open question:
Do supplier onboarding events also affect purchasing approval rules?

Store these as structured, versionable records.

Do not treat every LLM-generated record as confirmed.

Allow users to approve, reject, or correct extracted decisions.

Approved records should remain available across future conversations.

When a decision changes, retain its history.

## 9. Volatility discovery engine

This is the core intelligence of Galvanise.

Implement an initial volatility-discovery workflow that identifies:

- Change drivers
- Expected future changes
- Potentially stable decisions
- Independently changing concerns
- Business ownership
- Estimated change horizon
- Relevant technical dependencies
- Uncertainty
- Architectural risks

Distinguish between:

1. Observed volatility — supported by historical changes or incidents.
2. Anticipated volatility — supported by plans, requirements, and stakeholder statements.
3. Technical instability — complexity, coupling, and fragile dependencies.

Do not equate high Git churn with business volatility.

Do not require Git history to discover volatility.

Use structured Pydantic schemas for the results.

Each volatility hypothesis should include:

- ID
- Name
- Description
- Change driver
- Affected business decisions
- Expected stable decisions
- Time horizon
- Evidence references
- Evidence status
- Potentially affected technical components
- Open questions
- Recommended investigation

Do not fabricate numerical confidence scores.

## 11. Business-to-code traceability

Connect business requirements and decisions to technical implementation nodes.

For example:

```text
Supplier onboarding
    ↓
Supplier integration rules
    ↓
SupplierController
    ↓
PurchaseService
    ↓
SupplierAPIClient
```

Implement a retrieval-assisted matching process.

Use names, file paths, relevant source snippets, descriptions, graph neighbourhoods, and evidence.

Store mappings as traceability links.

Mark links as:

- Verified
- Human confirmed
- AI inferred
- Rejected

A dependency path must come from the actual graph. The AI must not invent graph edges.

Provide citations or file references for technical findings.

## 12. AI-generated stakeholder questions

The AI should detect when missing business information prevents it from making a reliable architecture recommendation.

For example:

"Do suppliers have different purchasing approval rules, or do they only use different communication protocols?"

Questions should be:

- Short
- Specific
- Relevant to an architectural decision
- Directed toward the appropriate stakeholder role when known
- Prioritised by their potential to change the proposed design

Users should be able to answer questions directly in chat.

The answer should update the persistent business model.

If information remains unknown, keep the uncertainty visible.

Do not implement automated email sending in the MVP.

## 13. Volatility-based decomposition

Implement an initial architecture recommendation engine.

The system should identify opportunities to isolate independently changing concerns.

Supported boundary types should include:

- Internal modules
- Interfaces
- Adapters
- Policy components
- Configuration boundaries
- Separately deployed services

Do not assume microservices are always superior.

For each proposed boundary, generate:

- Name
- Responsibility
- Related change drivers
- Stable contract
- Included technical responsibilities
- Excluded responsibilities
- Supporting evidence
- Dependencies
- Expected benefits
- Operational tradeoffs
- Migration considerations
- Open questions

Generate at least two candidate designs:

1. A conservative design preserving most of the existing architecture.
2. A volatility-aware design isolating independently changing decisions.

Where sufficient information exists, optionally generate a functionality-based comparison.

Do not pretend that these are objectively optimal designs.

## 14. Architecture evaluation

Build a lightweight scenario evaluation engine.

Users should be able to select a hypothetical business change, such as:

- Add a supplier.
- Change a pricing rule.
- Introduce a new warehouse.
- Replace an accounting provider.

Then compare the current and proposed architectures.

Evaluate:

- Potentially affected nodes
- Cross-boundary dependencies
- Changed interfaces
- Likely regression-test scope
- Operational tradeoffs
- Unverified assumptions

Use graph algorithms for structural calculations.

Clearly label estimates and unverified predictions.

Never present model-generated guesses as measured savings or proven reductions in maintenance cost.

If insufficient technical evidence exists, show a qualitative comparison instead of inventing numbers.
